## TL;DR

Chunking is now a pluggable strategy selected by one config flag. Two strategies exist
(`flat_baseline`, `hierarchical`), each with its own FAISS index, so they can be A/B tested
without one destroying the other. **No benchmark has been run yet** — that is the next step.

While doing this, two things turned out to be different from what we believed. Both are
written up below and both matter for the paper.

---

## What was done

### 1. `src/data/chunking/` — strategy interface
The single-module chunker became a package:

| File | What it holds |
|---|---|
| `base.py` | `Chunk` (`chunk_id`, `parent_chunk_id`, `strategy_id`, `level` + metadata) and `ChunkingStrategy` ABC |
| `flat.py` | `FlatChunker` — the original sliding window |
| `hierarchical.py` | `HierarchicalChunker` — parent/child |
| `splitters.py` | recursive splitting, heading cues, formula detection |
| `registry.py` | `get_chunker()` — the only place a strategy name is resolved |

`SimpleChunker` and `.split()` are kept as aliases, so `main.py` and anything else importing
them still works.

**Adding the graph strategy later = one entry in `STRATEGIES` in `registry.py`.** Nothing else.

### 2. OCR cleanup (`TextPreprocessor`)
Four new passes, run once per document upstream of both chunkers: hyphenation rejoin,
wrapped-line rejoin, page-artifact removal, repeated header/footer removal (kills the ETF
letterhead that was polluting chunk 0 of every document).

Gated by `OCR_CLEANUP`. With it off, flat output is byte-identical to the old chunker.
Queries are deliberately **not** cleaned — these passes fix scanned PDFs; stripping "page
numbers" out of a student's question would be wrong.

`PDFLoader` and `OCRHandler` now join pages with `\f` instead of `\n`, so the `page` metadata
field has a real value. Previously page boundaries were destroyed at load time.

### 3. Per-strategy artifacts
```
data/processed/<strategy>/chunks.jsonl          canonical, full metadata
models/vectorstore/index_<strategy>.faiss
models/vectorstore/metadatas_<strategy>.json
models/vectorstore/parents_<strategy>.json      hierarchical only, NOT embedded
```
`chunks.jsonl` is new because the old pipeline computed chunk metadata and then threw it away —
only text reached disk and `index_documents.py` re-derived `document`/`chunk_id` from the file
name. `parent_chunk_id` and `page` could never have survived that.

For hierarchical, **only child chunks are embedded**; parents are looked up by id at retrieval
time by `ParentAwareRetriever` and substituted in as context. Two children of one parent
collapse to that parent once.

### 4. `CHUNK_STRATEGY` switches the whole pipeline
`CHUNK_STRATEGY=flat_baseline|hierarchical` (`flat_512` is an accepted alias) selects chunker,
index and retrieval path with no code changes. `web/app.py` falls back to the legacy
`index.faiss` with a warning, so the current setup keeps working un-rebuilt.

## Two findings that change the paper

### Finding A: the baseline was never 512 tokens
It is **1024 characters**. Measured over all 205 files in `data/processed/`:
```
min=76  max=1024  mean=1000.8  median=1024.0
```
Nothing in the code overrides it. The strategy is therefore named `flat_baseline`, not
`flat_512`. Do not describe the baseline as 512 tokens in the paper.

### Finding B: `top_k` was silently capped at ~2 (fixed)
`ContextBuilder` had a hardcoded 2000-character budget. With 1024-char chunks and `top_k=5` it
appended chunk 1 (1024), truncated chunk 2 to 976, then stopped — **only 2 of 5 retrieved
chunks ever reached the LLM**. 2000/5 = 400 is why chunks looked like ~400 characters.

Consequences:
- `benchmarking/runs/baseline_topk5` was effectively a **top-k≈2** run. Do not compare it to
  anything collected from now on, and do not cite it as top-k=5.
- Now configurable via `CONTEXT_MAX_LENGTH` (default 6000).
- **When A/B testing, this value must be identical across runs**, or you measure context budget
  instead of chunking. A single 4500-char hierarchical parent alone exceeds the old 2000 cap.

### 1. Build both strategies over the full corpus
```bash
CHUNK_STRATEGY=flat_baseline python scripts/process_documents.py && \
CHUNK_STRATEGY=flat_baseline python scripts/index_documents.py
CHUNK_STRATEGY=hierarchical  python scripts/process_documents.py && \
CHUNK_STRATEGY=hierarchical  python scripts/index_documents.py
```
**This re-runs OCR on the six scanned PDFs at ~1–2 min/page** (D6). Budget real time, or pass
`--ocr-max-pages` for a quick smoke run first.

Sanity checks afterwards: hierarchical should yield ~3–4× more children than flat chunks, every
child row must have a `parent_chunk_id`, and `section` should be populated with `Clan N.`.

### 2. Retrieval metrics are now actually possible
Andrija's new question sets (`benchmark_realna_pitanja.json`, `finalna_pitanja.json`, 60 questions
each) carry per-question `sources` with `document`, `section` **and `pdf_pages`** — 63 source
entries have page numbers. The old set only had a document name.

This lines up with the chunking work: chunks now carry a real `page`, and `sources` in the query
response now carry `chunk_id`, `parent_chunk_id`, `strategy_id`, `section` and `page`. So
**page-level hit-rate@k is computable now** and no longer needs manual gold-chunk labelling.
That was the open question from the earlier session — it is now answerable.

Note the new set also has `required_facts` / `disallowed_claims` per question, and its own
`evaluation_notes` says the existing scripts do not score them yet. And `expected_behavior`
includes `abstain` (3) and `clarify` (1) — questions where the correct behaviour is *not* to
answer. Hit-rate@k is meaningless for those; exclude them.

### 3. Run the A/B
Same questions, same rubric, **same `CONTEXT_MAX_LENGTH`, same top_k, same embedding model,
same LLM, same prompt** — only `CHUNK_STRATEGY` varies.

One fairness caveat: parent de-duplication means hierarchical at `top_k=5` can return fewer
distinct passages than flat at `top_k=5` (observed: 5 child hits → 4 unique parents). The thing
to hold equal is the character budget, not the passage count. Say so in the paper.

### 4. Open question for the paper
Early signal only, not a benchmark: on one query the hierarchical top hit scored **0.851** vs
flat's **0.690**. Smaller children match a specific question better. Worth watching whether that
holds across the full set — if it does, it is a result worth reporting.

```
CHUNK_STRATEGY=flat_baseline     # | hierarchical   (flat_512 = alias)
OCR_CLEANUP=true
HIER_PARENT_SIZE=4500            # characters, not tokens (~3.5 char/token, sr)
HIER_PARENT_MIN=3600
HIER_CHILD_SIZE=1200
HIER_CHILD_MIN=900
HIER_CHILD_OVERLAP_RATIO=0.12
HIER_EXPAND_TO_PARENT=true
CONTEXT_MAX_LENGTH=6000          # was hardcoded 2000 — see Finding B
```

Your `.env` has none of these, so defaults apply. **`CONTEXT_MAX_LENGTH` changes behaviour on
the next run** (2000 → 6000). That is the bug fix, not a regression.
